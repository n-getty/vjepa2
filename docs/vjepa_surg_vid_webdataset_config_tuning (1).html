TL;DR — what I'd change in the three configs

Five concrete edits, ordered by impact:

  1. Cut phase 2 from 250 → ~100 epochs, and drop phase 3 to 256 px / 64 frames (a temporal cooldown, not a spatial one). The official V-JEPA 2.1 ViT-L recipe is "256 / 16f pretrain → 256 / 64f cooldown" — there is no 384 or 512 px config for ViT-L 2.1 anywhere in Meta's repo. Adding frames buys phase-recognition accuracy more cheaply than adding pixels.
  2. Lower start_lr in phase 1 to ~3e-5 (you're warming up from a pretrained checkpoint, not from scratch — the official's 1e-4 start_lr is for full from-scratch training). Keep peak lr=5.25e-4.
  3. Flip weight_distance_loss: false in the cooldown. The official 2.1 cooldown YAML does this; you currently have it true in cooldown too. Free win.
  4. Raise effective global batch to ≥64 (currently 16 = 4 GPUs × bs 4). Below ~32 global, JEPA's EMA teacher destabilises. Add gradient accumulation if memory won't fit batch_size: 8 directly.
  5. Reconsider the equal weighting. You picked uniform, which is defensible — but it gives a 5 h corpus (EndoVis15) the same gradient share as surgvu24 / surgtoolloc2022 (the two corpora closest to most downstream test sets). V-JEPA 2 itself uses non-uniform weights (HowTo100M at 0.565) for this exact reason. Worth A/B-ing.

Things to watch out for

  • EMA collapse risk: ema=[0.99925, 0.99925] constant + batch 16 global + warming straight to 5.25e-4 from a pretrained checkpoint is fragile. Mitigation: lower start_lr, monitor student-feature variance.
  • 512 px + RoPE interpolation past 384 is untested in the official codebase. If you keep the 512 px phase, expect to debug.
  • Your starting checkpoint is distilled from ViT-G. Continued pretraining without an anchor loss will gradually wash out the distillation signal. Consider an alignment loss to the frozen original.

Things to keep exactly as you have them

  • Peak lr = 5.25e-4 (matches the ViT-G recipe that produced your checkpoint)
  • weight_decay = 0.04 (universal across JEPA configs)
  • Mask schedule 8 × 0.15² + 2 × 0.7² (untouched across every JEPA scale; well-ablated)
  • predict_all: true, shift_by_n: 0 (definitional to V-JEPA 2.1)
  • n_registers: 0 — because you're continuing from a checkpoint. Adding registers fresh into a pretrained model is harmful. For a from-scratch run you'd want 4–8.
  • Continuing from vjepa2_1_vitl_dist_vitG_384.pt is correct — Surgical-DINO shows natural-image features need in-domain adaptation, and starting from a pretrained model strictly beats from-scratch at 1.3 k h.

Full report

Literature summary — JEPA family (state of the field, 2023–2026)

  • I-JEPA (Assran et al., 2023) establishes the two-principle masking rule that still governs all JEPA recipes: (a) target blocks must be semantically large (~0.15–0.2 of the image area), and (b) the context must be sufficiently informative / spatially distributed. Mask design is the single most ablated knob in the I-JEPA paper. (arxiv 2301.08243)
  • V-JEPA / VideoMix2M (Bardes et al., 2024) scales feature prediction to ~2M videos, ViT-H/16, tubelet 2×16×16, 90K iters, batch 3072, 224². It introduces the "multiblock" mask the user is using (8 small + 2 large spatial blocks, full-temporal). (arxiv 2404.08471)
  • V-JEPA 2 (Assran et al., 2025) scales to ≥1M hours of internet video (VideoMix22M) and introduces the warmup → constant → cooldown schedule. Reference run: 12K warmup + 228K constant + 12K cooldown iters at 256². Cooldown raises resolution and frame count and provides "8.4× GPU-time reduction" vs. training entirely at high-res, plus +0.7 pp from longer cooldown clips. Uses fixed (not ramp-up) EMA and weight decay. Tubelet 2×16×16, 3D-RoPE in predictor. (arxiv 2506.09985)
  • V-JEPA 2.1 (Meta, 2026) — repo-only, paper TODO. Refinements: (i) dense predictive loss — all tokens (visible + masked) contribute (predict_all: true); (ii) deep self-supervision at intermediate layers; (iii) image+video multimodal tokenizers; (iv) scale. Official ViT-L recipe (configs/train_2_1/vitl16): pretrain 256px/16f → cooldown 256px/64f (extends time, keeps spatial fixed). No 384px or 512px config exists for ViT-L 2.1. (github.com/facebookresearch/vjepa2)
  • Official ViT-L 2.1 hyperparameters (pretrain-256px-16f.yaml): lr=6e-4, start_lr=1e-4, final_lr=6e-4 (no decay in pretrain), warmup=40, epochs=1000, ipe=300, ipe_scale=1.25, ema=[0.99925, 0.99925] constant, weight_decay=0.04 constant, batch=24×128=3072 global, mask [8×0.15², 2×0.7²] full-temporal, predict_all=true, weight_distance_loss=true, shift_by_n=0, n_registers=0, modality_embedding=true, use_rope=true.
  • Official ViT-L 2.1 cooldown (cooldown-256px-64f.yaml): lr=6e-4, start_lr=1e-4, final_lr=1e-6, warmup=0, epochs=40, ema=[0.99925, 0.99925], dataset_fpcs=[64,64,64] (4× more frames), batch_size=12 (halved due to memory), weight_distance_loss=false, is_anneal=true, resume_anneal=true. So cooldown ≈ 4–5 % of pretrain epoch count, no warmup, peak LR same, decays to 1e-6.
  • Official ViT-G recipe that produced the teacher of the user's checkpoint: pretrain-256px-16f (lr=5.25e-4, epochs=800, warmup=40) → cooldown-256px-64f (epochs=40) → optional cooldown-384px-64f (epochs=40, lr=5.25e-4 → 1e-6, no warmup). The user's "5.25e-4 LR" target is exactly the ViT-G peak LR.
  • "Vision Transformers Need Registers" (Darcet et al., 2023) shows 4–16 register tokens remove high-norm artefact tokens that ViTs otherwise place in low-information patches; gives SOTA on dense prediction tasks and smoother attention. (arxiv 2309.16588) The V-JEPA 2.1 official configs ship with n_registers=0, but its dense-feature objective is exactly the regime registers help most.

Literature summary — Surgical / endoscopic SSL

  • Endo-FM (Wang et al., MICCAI 2023) — DINO-style teacher–student on ~45.7 h video (32,896 clips × 5 s avg), ViT-B/16 video transformer, 224² global / 96² local, 8–16 frames, EMA 0.996, LR 2e-5, 30 epochs. Augmentations kept: random flips, color jitter, Gaussian blur, solarization (all temporally consistent). Beats SAM on CVC-12k polyp seg with ~10× less data. (arxiv 2306.16741)
  • SurgeNet / SurgeNetXL (Jaspers et al., MICCAI-DEMI 2024 & 2025) — DINO-based, ~4.7 M surgical frames (image model, not video), CaFormer-S18 backbone, also ViT-S/B/L releases via DINOv1/v2/v3 at 224 or 336. Demonstrates that adding heterogeneous surgical data on top of procedure-specific data gives a further +2.5–5.2 % gain on segmentation / phase / CVS tasks. (arxiv 2407.17904)
  • SurgFM / Surg-3M (Che et al., 2025/26) — 938 h (4 K videos, 85 M frames), ConvNeXt + DINO + augmented distillation. Reports +8.4–9.5 pp Jaccard on phase recognition (AutoLaparo, M2CAI16, Cholec80), +10.3 pp mDice on CholecSeg8k vs second-best. This is the closest analog in scale to the user's 1,300 h corpus. (arxiv 2503.19740)
  • SurgVLP / HecVL / PeskaVLP (Yuan et al., MedIA 2025; MICCAI 2024; NeurIPS 2024) — contrastive vision–language on hundreds of YouTube surgical lectures + ASR; demonstrates the data-distribution lever: just paying attention to phase/text alignment yields zero-shot phase recognition. (SurgVLP arxiv)
  • Surgical-DINO (Cui et al., IPCAI 2024) — confirms that "zero-shot DINOv2 / naive fine-tune is not enough" for surgical depth — even strong natural-image features need surgical adaptation. Empirical evidence that the domain shift from natural video → surgery warrants in-domain SSL. (arxiv 2401.06013)

Top 5 biggest levers

  1. Cut main phase 250 → 80–120 ep, add temporal extension (32–64 f) to cooldown. Aligns with published V-JEPA 2.1 recipe; frees compute for the higher-leverage temporal axis.
  2. Skip 512 px; spend the saved compute on frames or batch size.
  3. Upweight surgvu24 + surgtoolloc2022. Uniform weighting gives 10 % weight to ~5 h corpora — they dominate noise floor, not test distribution.
  4. Raise effective global batch via grad-accum to ≥64. Below ~32 global, JEPA's EMA target destabilises.
  5. Mirror the official weight_distance_loss=true → false flip in cooldown. One-line change.

Top 3 watch-outs (subtle failure modes)

  1. EMA collapse from a too-stable teacher on too-small data. Effective half-life ~900 steps at batch 16 global × 1.3 k h means the teacher barely moves during warmup. With start_lr warming straight to 5.25e-4, the student can blow past the teacher in the first 2 epochs and the loss plateaus while features degrade.
  2. 512 px on a 384-pretrained checkpoint with use_rope=true and interpolate_rope=true is poorly tested. Rope interpolation past training resolution introduces frequency-domain artefacts.
  3. Your checkpoint is distilled from ViT-G. Continued pretraining without an anchor loss will gradually wash out the distillation signal. Either freeze the original ViT-G as an anchor (alignment loss term), or accept this is in-domain continued pretraining (not finetuning) and use small LR + short warmup.

Aurora scaling plan for the surg_vid 3-phase run

The relevant constraints

Aurora node: 6 Intel PVC GPUs × 2 tiles = 12 ranks/node, 64 GB HBM per tile. (Same per-tile memory as a V100, half an A100. The original configs were tuned on 80 GB A100, so per-rank batch should be smaller on Aurora, not larger.)

Dataset scale: 1.3 k h. At your 16-frame / 4-fps clips (4 s/clip), that's roughly 1.0–1.2 M unique clips. With 10 datasets the WebDataset shard counts you have are:

crcd, endovis15, jigsaw, miccai_2017, miccai_endoseg, surgvisdom1 each

This shard distribution is the binding constraint on node count (more on this below).

EMA stability floor: ≥32 global batch, ≥64 preferred — below this V-JEPA's teacher destabilises. (V-JEPA 2 paper appendix; I-JEPA also reports collapse at small batch + high EMA momentum.)

SSL "data pass" sweet spot: every clip seen 5–30 times across full training. Below 3× = underfit; above 50× = memorize. Total samples processed across all three phases is Σ(epochs × ipe × bs_global).

The trade-off

For a fixed corpus:

  • More nodes → larger global batch → more stable EMA, faster wall clock — but fewer shards/node (data diversity collapses) and fewer optimization steps for the same number of "passes" over data (which can hurt SSL where step count matters more than sample count).
  • Fewer nodes → smaller global batch (closer to the 32–64 floor) → noisier gradients, slower wall clock — but every node sees more shard diversity and you get more total optimizer steps.

For 1.3 k h, you're in the regime where gradient-step count is the more valuable axis (Endo-FM, SurgFM both report saturation curves bending around ~50k steps).

Rationale per phase:

Phase 1 (warmup, 4 nodes): Conservative node count protects the pretrained-checkpoint init — fewer ranks means a closer-to-32 effective gradient batch (after accounting for SSL's noisy targets) which lets the warmup actually warm up. Bumping ipe from 208 → 500 gives the LR scheduler more steps to ramp across, matching the official 2.1 recipe's longer warmup-iteration count. ~1 full pass through the corpus in 12 epochs is correct for a warmup.

Phase 2 (main, 8 nodes): This is where you spend wall clock. 8 nodes gives global batch 192, ipe 1000 across 100 epochs = 100k optimizer steps and ~17 data passes — squarely in the SSL sweet spot. The published V-JEPA 2.1 ViT-L recipe is ~300k steps but on 1000× more data; at our scale 100k steps is closer to "enough but not memorizing." bs_per_rank=2 because 384²/16f on 64 GB PVC tiles is tighter than on A100.

Phase 3 (cooldown, 4 nodes): 64 frames × 512² explodes the token count to 32k per clip — by far the heaviest per-sample workload. Drop back to 4 nodes / bs=1 / global 48. 12 epochs × ipe 400 = 4,800 cooldown steps, ~5% of phase-2 step count — exactly the official 2.1 cooldown ratio.

The shard-distribution catch

WebDataset's split_by_node assigns whole shards to nodes. You only have 1 shard for 6 of 10 datasets. At 8 nodes, those 6 datasets each visit only one node per epoch — gradient signal from CRCD, EndoVis15, JIGSAW, etc., is concentrated on a single rank instead of averaged across the fleet.

Two ways to handle this, in increasing order of effort:

  1. Cap phase 2 at the node count where most datasets still have ≥1 shard/node. With 5 shards in the smallest non-singleton (surgenet_robotic), that's ~5 nodes. I'd recommend 6 nodes for phase 2 (still global batch 144, ipe 1300) if you can't reshard.
  2. Reshard the singletons when you wire up the loader: split each 1-shard dataset into 8 shards by wds.ShardWriter(maxcount=…) with a smaller cap. ~30 min of work, lets you scale freely up to 8+ nodes without losing per-node diversity.

If your loader uses split_by_worker over a global URL list (instead of split_by_node), the shard-count constraint vanishes — every rank sees every shard probabilistically. Worth checking which mode you wire up.

Why not push to 16+ nodes?

You could — global batch 768 on phase 2 is fine for EMA. But:

  • ipe would need to drop to ~250 to keep data passes sane, leaving only 25k optimizer steps for the main phase (too few for SSL convergence at this corpus size — SurgFM saturates around 40k).
  • Shard distribution gets actively pathological (most datasets seen by ≤1 in 8 nodes per epoch).
  • Aurora wall-clock per phase is already short at 8 nodes — you're not compute-bound on cooldown.

The exception: if you reshard everything to ≥16 shards per dataset AND you're optimizing for wall-clock not for max representation quality, 16 nodes for phase 2 with ipe=500 and bs_per_rank=2 (global 384) is defensible.

Why 4 (not 6 or 8) when we lock it constant

The binding constraint is phase 2 — the workhorse — because it sets where you spend most compute.

  • Global batch 96 is comfortably above the EMA-stability floor (~32–64) so the teacher won't destabilise.
  • 100k optimizer steps lands squarely in the SurgFM / Endo-FM saturation window (40k–150k); going to 8 nodes would halve this to 50k for the same epoch budget, which is borderline-too-few for SSL.

The catch: 25k steps is below the SSL saturation floor

This is the one thing I'd push back on. SurgFM (~938 h, comparable scale) reports its quality curve saturating around 40–50k steps, not 25k. V-JEPA 2's published recipe used 252k iters. Below ~40k, you leave performance on the table — the EMA target needs time to drift into the data manifold, and below the floor the run finishes before that converges.

Why "more samples seen" isn't the same as "more optimizer steps" in JEPA

It's tempting to think: "if I double the global batch and halve ipe, I see the same samples — should be equivalent." For supervised learning that's roughly true. For JEPA-style SSL it is not, because the loss is computed against a target encoder that's an EMA of the student. That target only updates once per optimizer step, regardless of batch size.

With ema=[0.99925, 0.99925], the teacher's effective half-life is ln(2)/(1-0.99925) ≈ 924 steps. The teacher needs roughly 3–5 half-lives (~3,000–5,000 steps) to "forget" its initialization and start tracking the data, and another ~30,000–50,000 steps after that to actually drift into the surgical-data manifold and become a useful prediction target. Total floor ≈ 35–55k optimizer steps.

The two failure modes when you go below the floor:

  • Teacher never converges: the student is predicting against a target that's still partly the natural-video pretrained checkpoint, not surgical-domain features. Loss looks "fine" (it goes down) but downstream probes show the model hasn't actually learned surgical-specific representations — you basically did expensive feature extraction.
  • Student-teacher coupling never tightens: JEPA's whole game is the student learning to predict targets the teacher will later produce. With too few steps, you stop while that loop is still loose, leaving the predictor undertrained even if the encoder is fine.

Practical rule: at this scale (1.3 k h), aim for ≥40k optimizer steps in phase 2. The relationship is: 

opt_steps = epochs × ipe          # global batch is irrelevant to this count
samples_seen = opt_steps × global_batch    # batch only affects gradient noise

So when you scale to more nodes (larger global batch), don't divide ipe proportionally — keep ipe high enough that epochs × ipe ≥ 40,000. Extra samples-per-step is a free bonus (better gradient SNR); fewer optimizer steps is a penalty (worse EMA convergence). They are not interchangeable.

So the better dial is to keep step count above the floor, not divide ipe proportionally:

The "biggest dataset" question

I'd nudge this to the two biggest (surgvu24 + surgtoolloc2022), not one. Reasons:

  1. Shard count works out cleanly: 65 + 41 = 106 shards over 16 nodes = ~6.6 shards/node. No shard-distribution starvation.
  2. Coverage: surgvu24 alone is ~49 % of corpus bytes; adding surgtoolloc2022 brings it to ~81 %. So you'd be giving up only ~19 % of the data, but getting much more representational breadth across procedure types (surgvu24 is mostly nephrectomies/prostatectomies, surgtoolloc2022 is da Vinci tool-use clips — complementary).
  3. Overfit insurance: 100 epochs on one dataset risks the model learning that dataset's specific camera optics, lighting, post-processing pipeline as features rather than as nuisance. Two datasets with different acquisition setups makes the model marginalise those out.
  4. Both are exactly the corpora closest to most downstream test distributions — phase recognition benchmarks (Cholec80, AutoLaparo, M2CAI16) are all general laparoscopic surgery, much more similar to surgvu24/surgtoolloc2022 than to JIGSAW (training-task suturing) or SurgVisDom (virtual reality).

You'd lose: JIGSAW, EndoVis15, SITL, CRCD, miccai_2017, miccai_endoseg, surgenet_robotic, surgvisdom (combined ~19 % by bytes, mostly the niche/synthetic/training-data corpora).

You still see everything in phase 1 (12 ep warmup, all 10) and phase 3 (12 ep cooldown, all 10) — so the smaller datasets aren't forgotten, they just don't get the main-phase compute.

What I'd watch out for

  1. Phase 3 still uses all 10 datasets — the model has to "remember" the smaller ones in a 12-epoch cooldown. If you see the loss spike on the cooldown transition, the cause is likely under-exposure to small datasets in phase 2; mitigate by upweighting them in phase 3's datasets_weights.

  3. Per-dataset weighting in phase 2: I'd actually lean [1, 1] (equal between the two) rather than proportional-to-size, since surgtoolloc2022 has more tool-action diversity per hour.
