8 · Takeaways

  • Recipe fix: set lambda_progressive: false and lambda_value_vid: 0.0 in phase-2. The context loss as configured is actively harmful on this data scale.
  • Best operating point: phase-2 lambda_off pretrained to ~e229. Continued training beyond that mildly degrades probe-readable features.
  • EMA is a weak knob: alone it cannot rescue the λ regression. Scheduled EMA introduces a separate resume-discontinuity bug.
  • Probes agree on ranking (asformer vs triplet) for the catastrophic variants, but both compress the differences at the «good» end of the scale.
  • Phase-1 vs Meta-raw indistinguishable on the 20-epoch asformer probe (~42-45 F1 band) — BUT this was a probe bug, see §9.

9 · Probe-pipeline bug (root cause of the saturation)

The 20-epoch asformer probe was silently producing degraded encoder features on Aurora, capping every V-JEPA 2.1 backbone at ~42-47 F1. The Polaris reference (same Meta checkpoint) hit val_acc 78.68 / val_f1 71.78 on its 130-epoch run. Investigating this gap surfaced the bug.

Findings:

  • use_sdpa: true on Aurora XPU silently produces degraded encoder activations for the V-JEPA 2.1 model. Same weights, same data, same head — sdpa-on gives ~10 F1 at ep1, sdpa-off gives ~32-45 F1 at ep1.
  • v2.1 wrapper > v2.0 wrapper when both run with sdpa off. v8e (v2.1) reaches val_f1 70 at ep3; v8d (v2.0) needs ~7-8 epochs to get there.
  • v8e at epoch 3 already matches Polaris's 130-epoch best (val_acc 78.62 vs 78.68; val_f1 70.04 vs 71.78). The «20-epoch probe saturation» we'd attributed to the head was actually the sdpa bug.

9.3   Implications for the v2/v3/v4/v5/v6/v7 results

  • All those probes used use_sdpa: true with the v2.1 wrapper. Absolute F1 numbers were systematically depressed by ~15-25 points.
  • Relative rankings within those grids remain valid — all variants shared the same probe bias, so the ordering (e.g. lambda_off beats lambda_low, ema_low beats ema_sched) still holds.
  • Absolute conclusions need to be re-measured. Specifically: re-probing v5_lambda_off_e229 with the fixed recipe (v2.1 + no-sdpa + bs=2) is the priority — in flight as v8f.
  • The earlier «phase-2 plateau» and «saturation» verdicts may not hold once the probe can actually distinguish encoders.

10 · Where the encoder regression actually lives

With the corrected probe, we can finally measure the per-phase damage. Every surgical pretraining variant we’ve tried regresses the encoder vs Meta-raw. Phase 1 is short and high-rate; phase 2 is long and low-rate. Both cost real F1.

Backbonebest val_f1Δ vs MetaPretrain epochsF1 lost / epoch
Meta-raw (no surgical pretrain)79.38———
phase1_lowlr_384 e2 (low LR, 2ep)75.79−3.592~1.80
ngetty phase1_e12 (full warmup, 12ep)76.56−2.8212~0.24
lambda_off_e229 (12ep phase1 + 217ep phase2)54.91−24.47229~0.11 (amortized)

Reading the per-epoch column: phase 1’s damage rate is roughly an order of magnitude higher than phase 2’s. Phase 1 only looks harmless because it stops at epoch 12. Phase 2’s long horizon (200+ epochs) amasses cumulative damage despite a much lower per-epoch loss rate.

Decomposition of the −24.5 F1 total for lambda_off_e229:

  • ~−3 F1 attributable to phase 1 (matches the standalone phase1 ckpts).
  • ~−21 F1 from the additional 217 epochs of phase 2 (even with lambda_off).

What this means going forward:

  • Both phases regress the encoder. Earlier «phase 1 is harmless» framing was wrong — it’s just bounded.
  • To recover Meta-raw quality on this probe, either shorten/skip phase 1, or find a phase 1 recipe that actually helps (different LR/mask/EMA-init).
  • Phase 2 needs a real fix beyond removing the context loss. Even the cleanest grid variant amasses ~21 F1 of damage over 200 epochs.
  • Open question: can JEPA on our surgical data ever beat the Meta init on this probe, or is the data simply too narrow/redundant to add signal a frozen Meta backbone doesn’t already capture? Worth a controlled experiment with the new probe.

11 · Second probe-pipeline bug — sdpa layout in training

A separate one-line bug was found in app/vjepa_2_1/models/utils/modules.py::_sdpa (the helper used by both encoder and predictor during pretraining): an XPU-only path transposed q/k/v from [B,H,N,D] to [B,N,H,D] before calling F.scaled_dot_product_attention. SDPA always attends over dim −2, so this made it attend over the 16 heads and treat the 2048 tokens as heads. Cosine similarity vs reference: 0.017 isolated, 0.49 through the full encoder. Patched 2026-06-23 14:38 UTC; the buggy path is now opt-in via VJEPA_SDPA_BROKEN=1 for back-eval only.

Implication: every prior pretraining run (v2…v7 grids, all phase-1 / phase-2 chains) trained through scrambled attention. Their encoder weights are tuned for an op that no longer exists in the eval path. The §10 conclusion is therefore an artifact of train-vs-eval attention mismatch and is retracted.

11.2   Conclusions (using §10's framing)

  • Phase 1 with fixed sdpa is neutral, not harmful. 1 and 3 epochs both land within ±0.6 F1 of Meta-raw — run-to-run noise. The §10 «~1.8 F1 lost / epoch» figure was the broken-sdpa artifact.
  • The lambda_off −24.5 F1 gap is also an artifact. It measures the cost of evaluating broken-sdpa-trained weights with the fixed op, not a real encoder regression.
  • Phase 2 has not yet been re-measured under the fix. Until a fixed-sdpa phase 2 run lands, «phase 2 hurts the encoder» remains an open question, not a confirmed finding.
  • Open question shifts: does JEPA on surgical data help (not just «not hurt») under correct attention? Currently testing phase1_surgvu03 (surgvu24 weight 1.0 → 0.3, otherwise identical to phase1_baseline_v0) for a first signal on whether dataset rebalancing nudges phase 1 above the Meta-raw ceiling.
